**Architecture:** This is a Vue SFC (required by VitePress) but the visual sync logic is intentionally imperative/vanilla to demonstrate the event-based pattern. Vue is used only for mounting lifecycle and basic state (play/stop, bpm), NOT for beat-level reactivity.

**Implementation details:**

1. **Track setup (no wrapWith):**
```typescript
const bt = await createBeatTrack(urls, { numBeats: 16 })
// Note: NO wrapWith option — beats are plain objects
```

2. **DOM grid rendering:** Use Vue template to render the initial grid structure (3 tracks x 16 cells), but give each cell a data attribute or ref for direct DOM access:
```vue
<button
  v-for="(_, i) in 16"
  :key="i"
  :data-track="trackName"
  :data-beat="i"
  @click="toggleBeat(trackName, i)"
  class="beat-cell"
/>
```

3. **Beat active state management:** Since we're NOT using reactive Beat wrappers for the template, maintain a separate `activeStates` reactive map for the toggle UI (clicking cells). When user clicks a cell, update both the Beat object AND the activeStates map. The visual "active" class comes from Vue reactivity on this map (this is fine — the point is that the PLAYHEAD sync is event-based, not the pattern editing).

Actually, simpler approach: Use Vue reactive state for everything EXCEPT the playhead highlighting. The pattern editing (active/inactive) can use Vue bindings. The playhead (current step highlight) MUST use the event-based approach to demonstrate the pattern. This is the meaningful distinction.

4. **Event-based playhead sync (the core demo):**
```typescript
// Listen to beat events on the first track (all tracks are synchronized)
kickTrack.on('beat', (e) => {
  const { beatIndex } = e.detail

  // Direct DOM manipulation for playhead — NOT Vue reactivity
  document.querySelectorAll('.vanilla-beat-cell.current').forEach(
    el => el.classList.remove('current')
  )
  document.querySelectorAll(`.vanilla-beat-cell[data-beat="${beatIndex}"]`).forEach(
    el => el.classList.add('current')
  )
})
```

Use a unique CSS class prefix (e.g., `vanilla-beat-cell`) to avoid conflicting with other drum machine components on the page.

5. **Mute/solo:** Same pattern as Vue version — store original active states, toggle beats inactive when muted. Use Vue reactive state for the mute/solo toggle buttons (this is UI state, not audio sync).

6. **Cleanup on unmount:**
```typescript
onUnmounted(() => {
  beatTracks.forEach((track) => {
    track.off('beat', beatHandler)
    track.stop()
  })
})
```

7. **Controls:** Play/Stop button, BPM slider (60-200), mute/solo per track. Same UI layout as Vue version for easy comparison.

**Styling:** Match DrumMachineVue.vue styling but use `.drum-machine-vanilla` root class. Same VitePress theme variables, responsive grid, track colors. Add a subtle label or badge saying "Event-Based" to distinguish from Vue version.

# Drum Machine: Vanilla TS Event Pattern

<script setup>
import DrumMachineVanilla from '../.vitepress/theme/components/DrumMachineVanilla.vue'
</script>

Brief intro: This page demonstrates the event-based approach to drum machine UI sync. BeatTrack emits `beat` events at play time using AudioContext-aware timing, and we update the DOM directly. No reactive framework needed for the playhead.

<DrumMachineVanilla />

## How It Works

Explain the event-based pattern:
1. BeatTrack's lookahead scheduler schedules beats ~100ms ahead on the audio thread
2. Beat events fire at PLAY time (not schedule time) using `audioContextAwareTimeout`
3. `audioContextAwareTimeout` uses `requestAnimationFrame` + `audioContext.currentTime` for frame-accurate timing
4. Event handler updates DOM classes directly — the browser's next paint shows the correct step

## Key Code

Show the event listener setup:
```typescript
const kick = await createBeatTrack([...urls], { numBeats: 16 })
// No wrapWith needed — events handle sync

kick.on('beat', (e) => {
  const { beatIndex, active } = e.detail

  // Clear previous playhead
  cells.forEach(c => c.classList.remove('current'))

  // Highlight current step
  cells[beatIndex].classList.add('current')
})
```

## AudioContext-Aware Timing

Explain WHY this doesn't drift:
- Standard `setTimeout` drifts because it's based on the system clock
- `audioContextAwareTimeout` polls `audioContext.currentTime` via RAF
- The audio clock is hardware-driven and monotonic
- Visual updates happen on the same RAF frame as the timing check
- Result: audio and visual stay locked even over 2+ minutes of playback

Show the timing mechanism (simplified):
```typescript
// Inside audioContextAwareTimeout:
function scheduler() {
  const now = audioContext.currentTime * 1000
  tasks.forEach((task) => {
    if (task.due <= now)
      task.fn()
  })
  requestAnimationFrame(scheduler)
}
```

## Mute & Solo

Same pattern explanation as Vue page — toggling beat active states.

## Cleanup

Show the cleanup pattern:
```typescript
// Store references for cleanup
const beatHandler = (e) => { ... }
kick.on('beat', beatHandler)

// On teardown:
kick.off('beat', beatHandler)
kick.stop()
```

## When to Use This Pattern

- React (with refs or state + useEffect)
- Vanilla JavaScript / TypeScript
- Svelte, Angular, or any framework
- When you want explicit control over timing and DOM updates
- When reactive proxies aren't available or add unwanted overhead

## Comparison with Reactive Pattern

Brief table:
| Aspect | Reactive (Vue) | Event-Based (Vanilla) |
|--------|----------------|----------------------|
| Visual sync mechanism | `beat.currentTimeIsPlaying` auto-toggles | `track.on('beat', ...)` fires at play time |
| DOM update | Vue template re-render | Direct class manipulation |
| Setup | `wrapWith: reactive` | Event listener |
| Cleanup | Automatic (Vue reactivity) | Manual `.off()` required |
| Best for | Vue, Solid.js | React, vanilla JS, any framework |
