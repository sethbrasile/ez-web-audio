<task type="auto">
  <name>Task 1: Identify brittle areas and hardening recommendations (MAINT-01)</name>
  <files>.planning/phases/12-comprehensive-audit/AUDIT-maintainability.md</files>
  <action>
Read all library source files and analyze for brittleness. Focus on:

1. **Tight coupling** — Classes that directly access internals of other classes (not through interfaces). Read base-sound.ts, sound.ts, track.ts, oscillator.ts and check how they interact with controllers. Check if controllers access sound internals directly.

2. **Fragile inheritance** — The class hierarchy (BaseSound -> Sound -> Track, BaseSound -> Oscillator, MusicallyAware mixin). Look for:
   - Methods that MUST be called in specific order (temporal coupling)
   - Overrides that call super but depend on super's implementation details
   - Protected methods that subclasses rely on but could change

3. **Hard-coded assumptions** — Magic numbers, assumed array indices, string literals used as keys, format assumptions.

4. **Missing defensive code** — Methods that don't validate inputs, assume non-null without checking, don't handle edge cases (empty arrays, zero values, negative values).

5. **State management risks** — Mutable state that's shared across play/stop cycles. State that could get out of sync (e.g., isPlaying flag vs actual AudioNode state).

6. **Connection chain fragility** — The audio routing chain (source -> filters -> connections -> gain -> pan -> destination). What happens if nodes are added/removed mid-playback?

<task type="auto">
  <name>Task 2: Evaluate forward-compatibility and v2 extensibility (MAINT-02)</name>
  <files>.planning/phases/12-comprehensive-audit/AUDIT-maintainability.md</files>
  <action>
Review the public API surface and internal architecture for v2 extensibility. Reference the v2 requirements in REQUIREMENTS.md (Spatial Audio, Advanced Audio, Framework Bindings) as future directions.

Evaluate:

1. **API extensibility** — Can new features be added without breaking existing consumers?
   - Can spatial audio (SPATIAL-01/02/03) be added to existing Sound/Oscillator classes without changing their API?
   - Can recording/capture (ADV-02) be added without breaking the connection chain?
   - Can microphone input (ADV-03) fit into the current class hierarchy?
   - Would framework bindings (REACT-01, VUE-01) need to wrap or extend existing classes?

2. **Sealed vs open design** — Are there places where classes are too closed for extension?
   - Are there methods that should be public but are private?
   - Are there interfaces that should exist but don't (making it hard to create alternative implementations)?
   - Can users create custom sound types that work with the library's utilities (collections, crossfade, etc.)?

3. **Type constraints** — Are TypeScript types too narrow or too wide?
   - Union types that would need expanding for new features
   - Interfaces that are too specific (should be more generic)
   - Type parameters that should be generic but aren't

4. **Module structure** — Is the current file/module organization compatible with tree-shaking and separate package extraction (e.g., `ez-audio/react`, `ez-audio/spatial`)?
