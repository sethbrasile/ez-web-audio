For each test file, evaluate:

1. **False positives** — Tests that would pass even if the feature were broken:
   - Tests that only check that a function doesn't throw (but don't verify output)
   - Tests that mock so heavily the real code path isn't exercised
   - Tests that check `toBeDefined()` or `toBeTruthy()` when a specific value should be checked
   - Tests with no assertions at all

2. **Weak assertions** — Tests that assert too little:
   - Checking `toHaveBeenCalled()` without checking arguments
   - Checking array length but not contents
   - Checking type but not value
   - Using `toMatchObject()` when exact match would be better

3. **Missing edge cases** — For each class, identify untested scenarios:
   - What happens with empty/null/undefined inputs?
   - What happens at boundary values (0, negative, very large)?
   - What happens when called in wrong order (play before load, stop when not playing)?
   - What happens with rapid successive calls (double-play, play-stop-play)?
   - Error paths — are catch blocks tested?

4. **Test organization** — Are tests well-structured?
   - Are describe blocks logically grouped?
   - Are test names descriptive of behavior (not implementation)?
   - Is setup/teardown properly handled?
   - Are there tests that depend on execution order?

5. **Coverage gaps** — Which source files have NO corresponding test file?
   - Check: src/note.ts, src/sampled-note.ts, src/font.ts, src/events/event-types.ts
   - Check all files in src/interfaces/, src/errors/
   - Check src/utils/create-time-object.ts, src/utils/frequency-map.ts, src/utils/prop-access.ts, src/utils/timeout.ts
