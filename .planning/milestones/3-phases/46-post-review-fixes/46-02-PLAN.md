**Bug:** In `onPlayRamp()` at line 262-264, the `in()` method calls `this.onPlaySet(type).to(startValue)` then `this.onPlaySet(type).to(endValue).endingAt(...)`. The second call filters out the startValue via the dedup logic at line 226 (`this.startingValues = this.startingValues.filter(v => v.type !== type)`).

**Fix:** In the `in()` method (line 262-264), replace the two `onPlaySet` calls with direct array manipulation:

```typescript
in: (endTime: number) => {
  this.valuesAtTime.push({ type, value: startValue, time: 0 })
  this.addRampValue({ type, value: endValue, time: endTime }, rampType ?? 'exponential')
}
```

This pushes the startValue directly to `valuesAtTime` with time 0 (bypassing the startingValues dedup filter), then adds the endValue as a ramp. The `setValuesAtTimes()` method in subclasses will apply the time-0 value first, then schedule the ramp.

**Fix in base-sound.ts:**

1. Add `protected _targetGain: number = 1` field alongside the existing protected fields (near line 90).

2. In `changeGainTo()` (line 644), after the validation checks and before `this.controller.update(...)`, add:
   ```typescript
   this._targetGain = value
   ```

3. In the `volume` setter (line 1079-1081), no change needed -- it delegates to `changeGainTo()` which now sets `_targetGain`.

4. In `fadeOut()` (line 1150-1163): Do NOT modify `_targetGain`. The fade only affects the gainNode for the current playback cycle. No changes needed to fadeOut itself.

5. In `fadeIn()` (line 1127-1132): Change `const targetGain = this.gainNode.gain.value` to `const targetGain = this._targetGain` so fadeIn ramps to the user's intended gain, not whatever the node happens to be at.

6. Update the `volume` getter (line 1075-1077) to return `this._targetGain` instead of `this.gainNode.gain.value`. This ensures volume always reflects the user's intent, not a transient fade state.
