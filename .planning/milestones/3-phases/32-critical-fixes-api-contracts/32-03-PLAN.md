  <name>Task 1: Fix AudioSprite loop bug</name>
  <files>src/sprite.ts</files>
  <action>
In `src/sprite.ts`, the `play()` method at line 198 calls:
```
source.start(this.audioContext.currentTime, offset, duration)
```

When `sprite.loop = true` AND `source.loop = true` (set at line 165), passing a `duration` argument to `source.start()` causes the source to stop after that duration even though loop is set. The Web Audio API spec says: when duration is specified, the source stops after that many seconds regardless of the loop property.

Fix: Conditionally omit the duration argument when the sprite is configured to loop.

Change line 198 from:
```typescript
source.start(this.audioContext.currentTime, offset, duration)
```
to:
```typescript
if (sprite.loop) {
  // Do not pass duration when looping — duration arg stops the source after
  // that many seconds regardless of the loop property (Web Audio API spec)
  source.loop = true
  source.loopStart = offset
  source.loopEnd = sprite.end
  source.start(this.audioContext.currentTime, offset)
} else {
  source.start(this.audioContext.currentTime, offset, duration)
}
```

Also remove the earlier `source.loop = sprite.loop ?? false` on line 165 since we now set it conditionally in the start block. Replace it with just `source.loop = false` as the default, or remove it entirely and let the if/else handle loop setup. The cleanest approach: remove line 165 (`source.loop = sprite.loop ?? false`) and handle all loop setup in the conditional block above.

Wait -- non-looping sprites also need `source.loop = false` which is the default, so just removing line 165 is fine. But to be explicit and clear, keep line 165 as `source.loop = false` (the default) and override it to `true` inside the `if (sprite.loop)` block.

<task type="auto">
  <name>Task 2: Fix stale setTimeout _isPlaying corruption in BaseSound</name>
  <files>src/base-sound.ts</files>
  <action>
The problem: In `playAt()`, `this.setTimeout()` is called to set `_isPlaying = true` (for scheduled future plays) and `_isPlaying = false` (after duration elapses). These timeout IDs are never stored. If `stop()` is called and then `play()` is called again quickly, the old timeout from the first play can fire and corrupt the `_isPlaying` state of the second play.

Fix approach:
1. Add a `clearTimeout` function alongside `setTimeout` on BaseSound. In the constructor, after setting up `this.setTimeout`, also store `this.clearTimeout`:

   Add to the `BaseSoundOptions` interface:
   ```typescript
   clearTimeout?: (id: number) => void
   ```

   Add a protected property on BaseSound:
   ```typescript
   protected clearTimeout: (id: number) => void
   ```

   In the constructor, after the setTimeout setup block (around line 186), set up clearTimeout:
   ```typescript
   if (opts?.clearTimeout) {
     this.clearTimeout = opts.clearTimeout
   } else {
     this.clearTimeout = audioContextAwareTimeout(audioContext).clearTimeout
   }
   ```

   Wait -- actually `audioContextAwareTimeout` returns both setTimeout and clearTimeout together. The current code only takes setTimeout. Refactor to store both from the same call:

   In the constructor (around lines 180-187), change:
   ```typescript
   if (opts?.setTimeout) {
     this.setTimeout = opts.setTimeout
   } else {
     this.setTimeout = audioContextAwareTimeout(audioContext).setTimeout
   }
   ```
   to:
   ```typescript
   if (opts?.setTimeout) {
     this.setTimeout = opts.setTimeout
     this.clearTimeout = opts?.clearTimeout ?? (() => {})
   } else {
     const timer = audioContextAwareTimeout(audioContext)
     this.setTimeout = timer.setTimeout
     this.clearTimeout = timer.clearTimeout
   }
   ```

2. Add a private array to track pending timeout IDs:
   ```typescript
   private _pendingTimeoutIds: number[] = []
   ```

3. Create a private helper that wraps setTimeout and tracks the ID:
   ```typescript
   private _trackedTimeout(fn: () => void, delayMillis: number): number {
     const id = this.setTimeout(fn, delayMillis)
     this._pendingTimeoutIds.push(id)
     return id
   }
   ```

4. Create a private method to cancel all pending timeouts:
   ```typescript
   private _cancelPendingTimeouts(): void {
     for (const id of this._pendingTimeoutIds) {
       this.clearTimeout(id)
     }
     this._pendingTimeoutIds = []
   }
   ```

5. In `playAt()` (around line 913), at the very beginning of the method (before `this.setup()`), call `this._cancelPendingTimeouts()` to clear stale timeouts from any previous play.

6. In the `stop()` inner function (around line 1042), call `this._cancelPendingTimeouts()` at the start of the `stop` closure, before setting `_isPlaying = false`.

7. Replace all `this.setTimeout(` calls in `playAt()` and `playFor()` and `stopAt()` with `this._trackedTimeout(`:
   - Line 869: `this.setTimeout(() => this.stop(), duration * 1000)` -> `this._trackedTimeout(() => this.stop(), duration * 1000)`
   - Line 938: `this.setTimeout(() => { this._isPlaying = true }, ...)` -> `this._trackedTimeout(() => { this._isPlaying = true }, ...)`
   - Line 985: `this.setTimeout(() => { this._isPlaying = false }, ...)` -> `this._trackedTimeout(() => { this._isPlaying = false }, ...)`
   - Line 1063: `this.setTimeout(() => { stop() }, ...)` -> `this._trackedTimeout(() => { stop() }, ...)`
   - Line 1112: `this.setTimeout(fn, 1)` in `later()` -> `this._trackedTimeout(fn, 1)`
  </action>
  <verify>Run `pnpm typecheck` and `pnpm test` to confirm all tests pass. The key behavioral check: stop() now cancels pending timeouts, preventing stale _isPlaying corruption.</verify>
  <done>All setTimeout calls in BaseSound are tracked. stop() and playAt() cancel pending timeouts. Stale timeouts from previous play cycles cannot corrupt _isPlaying state.</done>
