## Critical Findings

### C1. `.d.ts` files use extension-less imports — breaks `moduleResolution: "nodenext"` consumers

- **Severity:** Critical
- **File:** Every `.d.ts` in `dist/`, generated by `vite-plugin-dts`
- **Evidence:** `dist/index.d.ts:1` — `import { TimeObject } from './utils/create-time-object'` (missing `.js` extension). The `.js` files use extensions correctly (Rollup handles this), but `vite-plugin-dts` does not rewrite `.d.ts` imports to match. Additionally, 4 type-only `.d.ts` files have no `.js` counterpart at all: `dist/events/event-types.d.ts`, `dist/interfaces/connectable.d.ts`, `dist/interfaces/playable.d.ts`, `dist/utils/exponential-ratio.d.ts`.
- **Impact:** 30+ TS2835 errors for any consumer using `moduleResolution: "nodenext"` or `"node16"`. Most bundler-based consumers (`"bundler"` mode) are unaffected, but `nodenext` is the recommended ESM resolution mode and is increasingly adopted.
- **Root cause:** `vite-plugin-dts` generates `.d.ts` files from TypeScript source imports (which are extension-less), while Rollup adds `.js` extensions to the emitted JS. The two output graphs are out of sync.
- **Fix:** Set `rollupTypes: true` in `vite-plugin-dts` config (`vite.config.js:13`). This bundles all declarations into a single `dist/index.d.ts`, eliminating cross-file `.d.ts` imports entirely. The `rollupOptions.input` entries for barrel files can then be removed since they're no longer needed.

## High Findings

### H1. `onPlayRamp().from(x)` silently discards the `from` value

- **Severity:** High
- **File:** `src/controllers/base-param-controller.ts:263-264`
- **Evidence:** The `in()` method on line 263-264 does:
  ```typescript
  this.onPlaySet(type).to(startValue)       // pushes {type, value: startValue} to startingValues
  this.onPlaySet(type).to(endValue).endingAt(endTime, rampType)  // filters startingValues by type (removing startValue!), then moves endValue to ramp arrays
  ```
  The second `onPlaySet(type).to(endValue)` call on line 264 triggers the dedup filter at line 226 (`this.startingValues = this.startingValues.filter(v => v.type !== type)`) which removes the `startValue` entry pushed by line 263. The `from` value is lost.
- **Impact:** `onPlayRamp('gain', 'linear').from(0.5).to(1).in(2)` does NOT set gain to 0.5 at time 0. The ramp starts from whatever the current gain happens to be. This is a core fluent API feature that's documented and advertised — and it doesn't work. The existing test at `base-param-controller.test.ts:199-209` validates this broken behavior (asserts `startingValues` is empty after `onPlayRamp`, which is the bug).

### H2. Landing page drum machine and effects examples use nonexistent API

- **Severity:** High
- **File:** `docs/index.md:58-76`
- **Evidence:**
  - **Drum machine** (lines 58-65): `createBeatTrack(kick, 8)` — actual signature is `createBeatTrack(urls: string[], opts?: BeatTrackOptions)`. `setPattern()` doesn't exist. `playLoop()` doesn't exist.
  - **Effects** (lines 70-76): `createFilterEffect({ type: 'lowpass', frequency: 800 })` — actual signature is `createFilterEffect(type: FilterType, options?)`. Type is the first positional argument, not an options property.
- **Impact:** Two of four landing page examples produce runtime errors if copied. These are the first code a prospective user sees. The "Play a Sound" and "Create a Synthesizer" examples are correct.

## Medium Findings

### M1. `fadeOut()` and Oscillator anti-click stop leave gain at 0 — next `play()` is silent

- **Severity:** Medium
- **Files:** `src/base-sound.ts:1150-1163` (fadeOut), `src/oscillator.ts:411-421` (stopAt anti-click)
- **Evidence:**
  - `fadeOut()` ramps `gainNode.gain` to 0 via `linearRampToValueAtTime(0, ...)`. After stop, the gain node retains value 0.
  - Oscillator's `stopAt()` does a 10ms anti-click fade to 0 on the persistent `gainNode`.
  - `Sound.setup()` does not touch gain at all — only creates a new AudioBufferSourceNode.
  - `Oscillator.setup()` captures `this.gainNode.gain.value` (which is 0 post-fade) and "restores" 0.
  - No `_userGain` or similar field exists to track the intended gain separately from the node's current value.
- **Impact:** After any `fadeOut()` on Sound/Track/Oscillator, or after stopping an Oscillator, the next `play()` produces silence. User must manually call `changeGainTo()` to recover. No tests exist for "play after fadeOut" scenarios.

### M2. Additional doc code examples broken (non-landing pages)

- **Severity:** Medium
- **Files/evidence:**
  - `docs/examples/effects.md:309` — `createAnalyzer(ctx, { ... })` missing `await`. Returns a Promise; subsequent `sound.setAnalyzer(analyzer)` receives a Promise object.
  - `docs/examples/effects.md:316-321` — uses raw AnalyserNode methods (`new Uint8Array(analyzer.frequencyBinCount)`, `analyzer.getByteFrequencyData(dataArray)`) instead of the Analyzer wrapper API (`analyzer.getFrequencyData()` which returns pre-allocated arrays).
  - `docs/examples/layered-sound.md:89,102` — event handlers destructure `({ time })` and `({ message, failedLayers })` directly from the event, but the `on()` listener receives a `CustomEvent` whose data is on `.detail`, not the event root. Correct: `(event) => { const { time } = event.detail }` or `({ detail: { time } })`.

## Appendix: Filtered Issues (For Future Discussion)

These were identified by reviewers but deemed not actionable for this cycle. Preserved here for later discussion.

### F1. Track.seek() uses 1ms delay via `this.later()` creating brief gap

- **File:** `src/track.ts:323`
- **What:** When seeking while playing, `stop()` is awaited then `play()` is deferred by 1ms via `this.later(() => this.play())`. During that window, `_isPlaying` is false and there's a brief audible gap.
- **Why filtered:** Works correctly in practice. The 1ms gap is imperceptible. The `later()` call may exist to avoid a synchronous stop→play within the same microtask (possibly to let the AudioBufferSourceNode fully disconnect). Removing it could introduce a different bug.
- **Discussion angle:** Is the `later()` actually needed? Could `play()` be called directly after `await this.stop()`?

### F2. Track.stop() sets startOffset=0 before super.stop()

- **File:** `src/track.ts:241-255`
- **What:** `this.startOffset = 0` is set before `super.stop()` is called. If any code reads `position` between the offset reset and the actual stop, it would see position 0 while audio is briefly still playing.
- **Why filtered:** The `onended` handler is nullified before `super.stop()`, so no event handler will read position in that window. No external code path reads position during stop. No practical impact.
- **Discussion angle:** Pure ordering hygiene — could move `startOffset = 0` after `super.stop()` for clarity.

### F3. Progress counter in `createSounds`/`createTracks` could report non-sequential values

- **File:** `src/index.ts:331-341`
- **What:** `loaded++` inside concurrent promises. If two `decodeAudioData` calls resolve on the same event loop tick, the progress callback could fire with values like (2, 5, url_a) then (3, 5, url_b) rather than strictly sequential.
- **Why filtered:** JavaScript is single-threaded. Each `await` yields back to the event loop, so `loaded++` executes atomically per callback. The ordering of callbacks may not match URL order, but the count itself is always correct. Progress bars will work fine.
- **Discussion angle:** If strict ordering matters, could use `Promise.allSettled` with sequential reporting, but this adds complexity for no real benefit.

### F4. `BaseSound` uses deprecated `SoundEventMap` instead of `BaseSoundEventMap`

- **File:** `src/base-sound.ts:80`
- **What:** `export abstract class BaseSound extends TypedEventEmitter<SoundEventMap>` — `SoundEventMap` is the deprecated alias for `TrackEventMap`. Sound instances type-check for `on('pause', ...)` which never fires.
- **Why filtered:** Changing `BaseSound` to use `BaseSoundEventMap` would break `Track.emit('pause', ...)` since Track inherits from BaseSound and relies on the base class generic parameter including pause/resume/seek events. Fixing this requires either: (a) Track overriding the generic parameter (complex TypeScript), or (b) Track using a separate emit path. This is an architectural constraint, not a simple change.
- **Discussion angle:** Could be addressed in a future "event system v2" refactor. The deprecated type annotation guides consumers to the correct maps in the meantime. The practical impact is just misleading autocomplete — no runtime bugs.

### F5. `_disposeUnmute` tests only check "doesn't throw" — weak assertions

- **File:** `src/index.test.ts:788-807`
- **What:** All three `_disposeUnmute` tests only verify the function doesn't throw. None verify that calling `_disposeUnmute()` actually invokes the dispose handle returned by `unmuteIosAudio`. A no-op implementation would pass.
- **Why filtered:** `_disposeUnmute` is an internal function (`@internal`, underscore-prefixed) that cleans up iOS event listeners from the third-party `unmute.js`. The real cleanup behavior depends on the vendor library. Risk of this regressing is low.
- **Discussion angle:** Could mock the `_unmuteDispose` function reference and assert it's called, but this would test implementation details rather than behavior.

### F6. `createNotes()` does not populate `letter`, `accidental`, or `octave` on Note objects

- **File:** `src/index.ts:162-175`
- **What:** `createNotes()` builds Note objects from a frequency map JSON but only sets `noteObject.frequency`. It does not parse the key string (e.g., "A4", "Bb3") to populate the `letter`, `accidental`, or `octave` fields. Tests verify frequency is set but don't check musical identity fields.
- **Why filtered:** The `createNotes()` docstring only mentions frequency. This may be intentional — the function creates notes from an arbitrary JSON map where keys might not follow standard note naming. The Note class can have these fields populated separately.
- **Discussion angle:** If consumers expect `createNotes()` to return fully populated Note objects, this is a feature gap. Could parse standard note names where possible and leave fields undefined for non-standard keys.

### F7. `Beat.pendingTimerIds` grows unbounded during long playback sessions

- **File:** `src/beat.ts:188-192`
- **What:** `trackedTimeout` appends timer IDs to `pendingTimerIds` but they're only cleared when `cancelPendingTimers()` is called (on BeatTrack.stop). During a long drum machine session, this array accumulates thousands of completed timer IDs.
- **Why filtered:** This is a minor memory concern, not a correctness bug. The IDs are just numbers (8 bytes each). Even 10,000 beats = ~80KB. The array is cleared on stop. Not a practical problem.
- **Discussion angle:** Could self-remove IDs from the array when timers complete, but this adds overhead per beat. The current approach is simpler.
