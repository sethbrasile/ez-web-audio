    package.json
    playwright.config.ts
  </files>
  <action>
Install Playwright as a dev dependency:
```
pnpm add -D @playwright/test
```

Then install Playwright browsers (chromium only to keep CI fast):
```
pnpm exec playwright install chromium
```

Create `playwright.config.ts` in project root:
- Use `webServer` config pointing to `pnpm dev` (VitePress dev server on port 5173)
- Set `webServer.reuseExistingServer` to true for local dev
- Set `webServer.timeout` to 120000 (VitePress can be slow to start)
- Configure only Chromium (skip Firefox/WebKit to keep tests fast)
- Set `testDir` to `./e2e`
- Set `retries` to 1 for flaky network tests
- Set `use.baseURL` to `http://localhost:5173`
- Set reasonable timeouts: `timeout: 30000`, `expect.timeout: 10000`

Add script to package.json:
```json
"test:e2e": "playwright test"
```

Do NOT add Playwright to the CI workflow yet — this is for local verification.
  </action>

  <done>Playwright installed, configured for VitePress dev server, chromium browser ready, test:e2e script in package.json.</done>

Create `e2e/` directory and two test files.

**e2e/navigation.spec.ts:**

**e2e/demos.spec.ts:**
Test that each interactive demo component renders (NOT that audio plays — can't test audio in headless browser):

For each demo page, verify:
1. Page loads without errors (no uncaught JS exceptions)
2. Expected UI elements are present (buttons, controls, etc.)

Demo pages to test (check actual routes in docs/ directory structure):
- AudioDemo: Has a play button
- TrackDemo: Has play/pause controls
- OscillatorDemo: Has frequency controls or play button
- FilterDemo: Has filter type selector or controls
- DistortionDemo: Has a play button
- TimingDemo: Has timing-related controls
- DrumMachine: Has grid/beat elements and play button
- SynthKeyboard: Has piano keys (rendered keyboard)
- XYPad: Has canvas element
- SynthDrumKit: Has drum pad buttons
- SampledDrumKit: Has drum pad buttons
- SoundfontPiano: Has piano keys
- DrumMachineVue: Has grid and play button
- DrumMachineVanilla: Has grid and play button
- AmbientGenerator: Has controls
- VisualizationDemo: Has canvas or visualization area

For each page test:
```typescript
test('DemoName renders without errors', async ({ page }) => {
  const errors: string[] = []
  page.on('pageerror', err => errors.push(err.message))

  await page.goto('/examples/demo-path')
  await page.waitForLoadState('networkidle')

  // Check for specific UI element
  await expect(page.locator('button, [role="button"]').first()).toBeVisible()

  // No JS errors
  expect(errors).toHaveLength(0)
})
```

Adapt selectors to what each demo actually renders. Use generic selectors where possible (buttons, canvas, inputs) rather than component-specific class names to keep tests resilient.

NOTE: Some demo pages may lazy-load components. Use `waitForLoadState('networkidle')` or wait for specific elements. If a demo requires clicking "Init Audio" or similar button before content appears, click that button first.

Look at the actual page routes by checking the `docs/examples/` directory for `.md` files that define pages.
