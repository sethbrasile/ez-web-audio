  <name>Task 1: Audit API naming conventions, patterns, and approachability (DX-01, DX-03)</name>
  <files>.planning/phases/12-comprehensive-audit/AUDIT-developer-experience.md</files>
  <action>
Read `src/index.ts` to identify all public API surface (factory functions, exported classes, types, interfaces). Then read each public class and its methods.

Evaluate:

**DX-01: Naming Consistency**
- Do all factory functions follow the same naming pattern (e.g., `createX` vs `makeX` vs just `X`)?
- Do methods across classes use consistent verbs (e.g., `play/stop/pause` — are there any that use `start/halt/suspend` instead)?
- Are option types named consistently (e.g., `XOptions` vs `XConfig` vs `XParams`)?
- Are event names consistent across classes?
- Do type/interface names follow a consistent convention?

**DX-03: Approachability Review**
- Review from the perspective of a developer who knows JavaScript but NOT Web Audio API.
- Are there methods/properties that expose Web Audio internals unnecessarily (e.g., requiring users to know about AudioBufferSourceNode, GainNode, AudioParam)?
- Is the "happy path" for common tasks obvious and short?
- Are there confusing method signatures (too many parameters, unclear parameter names)?
- Does the fluent API (`update().to().from()`) make sense to someone who hasn't read the docs?
- Are there APIs where the user needs to understand internal sequencing (e.g., must call X before Y)?

**DX-02: Abstraction Quality**
Review the class hierarchy and module structure:
- Read src/base-sound.ts, src/sound.ts, src/track.ts, src/oscillator.ts — is the inheritance hierarchy justified? Is there unnecessary complexity?
- Read src/controllers/ — do the controllers add value or just add indirection?
- Read src/interfaces/ — are Playable/Connectable the right abstractions?
- Are there operations that require touching multiple classes when they should be one call?
- Are there classes doing too much (God objects)?
- Are there missing abstractions that would simplify common tasks?
- Is the mixin pattern (MusicallyAware) adding complexity without enough value?

**DX-04: Error Messages and Edge Cases**
Read ALL error classes in src/errors/ and ALL throw/console.error/console.warn statements across the library:
- For each error message, evaluate: Does it tell the user WHAT went wrong AND HOW to fix it?
- Are there edge cases that silently fail instead of throwing?
- Are there error messages that reference internal implementation details instead of user actions?
- Are there missing validations (e.g., calling play() before audio is loaded, invalid BPM values)?
- Check debug messages in src/debug/ — are they helpful or noisy?
