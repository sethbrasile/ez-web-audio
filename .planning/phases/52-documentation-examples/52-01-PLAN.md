# Plan 52-01: Fix Documentation Examples and Add Soundfont Performance Caveat

## Goal

Fix three documentation inaccuracies: the vibrato example that silently breaks due to consume-once semantics, the README seek example that incorrectly shows `await`, and the missing soundfont performance caveat for large files on mobile.

## Context

- `onPlayRamp` schedules are consumed after one `play()` call. The vibrato example in `docs/guide/parameter-control.md` schedules multiple ramps in a while loop, but only the **last** ramp survives because each `onPlayRamp` call for the same parameter replaces the previous one. The example is fundamentally misleading.
- `Track.seek().as()` returns `void`, not a `Promise`. The README shows `await song.seek(30).as('seconds')` which is incorrect.
- `createFont()` calls `mungeSoundFont()` synchronously to parse base64-encoded audio data. For large soundfont files (5-20 MB), this blocks the main thread and can freeze the UI on mobile devices. This limitation is not documented anywhere.

<file>docs/guide/parameter-control.md</file>
<action>
Replace the vibrato example (lines ~103-115) with a corrected version that explains the consume-once limitation. The fix should:

1. Replace the current `addVibrato` function with a simpler, correct example that demonstrates a single pitch bend or a brief ramp sequence
2. Add a clearly visible note/callout BEFORE the example explaining that `onPlaySet` and `onPlayRamp` schedules are **consumed after one play** -- they must be re-scheduled before each `play()` call if you want the effect to repeat
3. The note should explain that calling `onPlayRamp` multiple times for the **same parameter** replaces the previous schedule (last-write-wins), so the while-loop approach shown previously cannot create true vibrato

Here is the replacement content. Replace the `### Vibrato (manual LFO)` section (from line 103 `### Vibrato (manual LFO)` through line 115 the closing triple-backtick) with:

```
### Vibrato (manual LFO)

::: warning Consume-once semantics
`onPlaySet` and `onPlayRamp` schedules are **consumed after one play call**. Calling `onPlayRamp` multiple times for the same parameter replaces the previous schedule (last-write-wins). True vibrato requires a real-time loop that re-schedules ramps — it cannot be built with a pre-play schedule alone.
:::

For a single pitch bend effect, scheduling works well:

\`\`\`typescript
// Bend from 440 Hz down to 220 Hz over 2 seconds on next play
osc.onPlayRamp('frequency').from(440).to(220).in(2)
osc.play()
// Schedule is now consumed — subsequent play() starts at the default frequency
\`\`\`

For continuous vibrato, use the Web Audio API's `OscillatorNode` LFO pattern directly or re-schedule before each play.
```
